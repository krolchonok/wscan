# Black-box разведка и поиск первоначального доступа

Документ описывает рекомендуемый сценарий работы `wscan` при разрешённом внешнем или внутреннем black-box пентесте. Перед началом должны быть согласованы диапазоны адресов, временное окно, допустимая нагрузка и разрешённый уровень воздействия.

## 1. Подготовка проекта

Оператор создаёт проект и задаёт:

- IP, hostname или CIDR;
- допустимые RPS и параллельность;
- сетевые таймауты и число повторов;
- исключённые адреса и сервисы;
- разрешённые типы проверок.

Безопасные начальные настройки:

- `AllowExploit = false`;
- `AllowCredentialAttack = false`;
- `AllowCodeExec = false`;
- умеренные RPS и concurrency;
- сначала discovery и read-only проверки.

Результат этапа — зафиксированная область работ и воспроизводимая конфигурация сканирования.

## 2. Обнаружение узлов

Для подсети выполняется поиск доступных машин:

- ICMP и альтернативные признаки доступности;
- TCP-подключения к распространённым портам;
- DNS и PTR;
- обнаружение узлов, блокирующих ping;
- повторная проверка сомнительных результатов.

Недоступный по ICMP, но отвечающий по TCP узел считается живым. Таймаут не является доказательством отсутствия узла. Обнаруженные адреса сохраняются в инвентарь проекта.

## 3. Поиск портов и сервисов

Сначала проверяются распространённые порты, затем при необходимости полный диапазон:

- TCP и выбранные UDP-порты;
- определение протокола и версии;
- TLS/SSL;
- SMB, LDAP, Kerberos, RDP, WinRM и DNS;
- SSH, FTP, базы данных и почтовые сервисы;
- промышленные и другие сетевые протоколы.

Если цель начинает сбрасывать соединения, сканер уменьшает нагрузку, применяет backoff и повторяет сомнительные порты. Такой результат отмечается как неполный, а не как «порт закрыт».

## 4. Анонимная AD-разведка

При обнаружении характерных AD-портов запускается AD-сценарий.

### DNS

Проверяются:

- доменные SRV-записи;
- DC, Kerberos, LDAP и Global Catalog;
- PTR-записи;
- возможность AXFR;
- соответствие доменов и контроллеров выбранной области.

Результат — имена домена, возможные контроллеры и адреса инфраструктуры.

### LDAP

Без учётной записи читается RootDSE:

- `defaultNamingContext`;
- домен;
- имя сервера;
- подтверждение AD DS.

Если разрешён anonymous bind, собираются:

- пользователи;
- пользователи без Kerberos pre-auth;
- владельцы SPN;
- учётные записи с `PASSWD_NOTREQD`;
- пароли без срока действия;
- unconstrained delegation;
- reversible password encryption;
- DES-only;
- объекты с `adminCount=1`.

Отказ LDAP фиксируется как `denied`, а не как отсутствие пользователей.

### SMB и SAMR

Проверяются:

- SMB dialect и SMBv1;
- обязательность SMB signing;
- NTLM-сведения об ОС, домене и имени машины;
- null session и guest;
- перечисление имён общих ресурсов;
- SAMR user enumeration, если оно разрешено сервером.

Имена из SAMR передаются в общий набор Kerberos-кандидатов.

### RDP и RPC

Собираются:

- NTLM metadata через RDP/CredSSP;
- доступность RPC-интерфейсов;
- возможность безопасного coercion discovery без callback;
- признаки известных SMB/RPC-уязвимостей.

## 5. Kerberos user enumeration

Имена из доступных анонимных источников объединяются и нормализуются:

```text
LDAP + SAMR/SMB + AS-REP-кандидаты
                 |
                 v
       нормализация и дедупликация
                 |
                 v
         AS-REQ без пароля
```

Если имён не найдено, проверяется минимальный baseline:

- `administrator`;
- `guest`;
- `krbtgt`.

Возможные результаты:

- `valid` — пользователь существует и KDC требует pre-auth;
- `valid-disabled` — пользователь существует, но отключён или заблокирован;
- `negative` — principal не существует;
- `confirmed` — AS-REP получен без pre-auth;
- `error` или `incomplete` — проверка не состоялась.

Пароль не отправляется, попытка входа не выполняется.

## 6. AS-REP roasting

Для кандидатов отправляется AS-REQ без pre-auth. Если у пользователя установлен `DONT_REQ_PREAUTH`, сканер получает:

- подтверждённое имя пользователя;
- Kerberos etype;
- строку `$krb5asrep$...` для Hashcat или John;
- finding высокой важности;
- защищённый файл экспорта.

Получение hash не означает, что пароль известен. Дальнейшая проверка стойкости пароля выполняется офлайн и только в пределах разрешения.

## 7. Проверки сервисов без учётных данных

После инвентаризации выбираются проверки, соответствующие обнаруженным сервисам:

- web misconfiguration и известные CVE;
- доступ без аутентификации;
- TLS-сертификаты и слабые настройки;
- SMB, FTP, SSH и базы данных;
- Redis, MongoDB и другие сетевые службы;
- DNS, SNMP и почтовые сервисы;
- совместимые native Nuclei/NSE-проверки.

Проверка default или empty credentials относится к credential attack и требует отдельного разрешения.

Положительный finding должен содержать цель, порт, протокол, доказательство, уровень воздействия и время проверки.

## 8. Получение первой учётной записи

Если получен или предоставлен пароль, NTLM hash либо TGT:

1. Учётные данные сохраняются в проекте.
2. Проверяется область их применимости.
3. Выполняется осторожная проверка на выбранных сервисах.
4. Учитывается lockout policy.
5. При неизвестной политике блокировки используется минимальное число попыток.

Password spraying и словарные атаки выполняются только при `AllowCredentialAttack`.

## 9. Аутентифицированная AD-разведка

С валидной доменной учёткой становятся доступны:

- пользователи, группы и компьютеры;
- администраторы и привилегированные группы;
- SPN и Kerberoastable accounts;
- delegation;
- доменный SID;
- trusts и контроллеры;
- AD CS и шаблоны сертификатов;
- BloodHound-подобный граф отношений;
- доступные SMB, WinRM и LDAP-ресурсы.

Чтение каталога должно быть отделено от действий, изменяющих состояние домена.

## 10. Kerberoasting

Обычный режим требует валидную доменную учётку. Альтернативные режимы используют готовый TGT либо пользователя без pre-auth вместе с явным списком SPN.

Порядок действий:

1. LDAP находит активные пользовательские SPN.
2. Машинные, отключённые учётные записи и `krbtgt` исключаются.
3. Запрашиваются сервисные билеты.
4. Ciphertext экспортируется в формате Hashcat.

Полученный TGS hash не доказывает компрометацию. Проверка пароля выполняется офлайн.

## 11. AD CS

При LDAP-доступе анализируются:

- центры сертификации;
- опубликованные шаблоны;
- EKU и application policies;
- enrollment и name flags;
- необходимость approval и signatures;
- ACL шаблонов;
- кандидаты ESC1, ESC2, ESC3, ESC4 и ESC9.

Без учётки ищутся web enrollment и доступные AD CS endpoints. Найденная конфигурация считается кандидатом, пока эффективные права и путь эксплуатации не подтверждены отдельно.

## 12. Активные проверки первоначального доступа

Только после подтверждения оператором включается `AllowExploit`.

Возможные сценарии:

- SQL injection;
- LFI и path traversal;
- unrestricted file upload;
- подтверждение RCE уникальным маркером;
- exploit-шаблоны;
- SMB/RPC coercion с локальным callback;
- MSSQL `xp_cmdshell` и передача файлов;
- другие действия, способные изменить цель.

Перед запуском фиксируются конкретные хосты, ожидаемое воздействие, создаваемые файлы, callback-адрес, способ очистки и временное окно.

## 13. Coercion

### Discovery

- Проверяется доступность RPC bind.
- Callback не вызывается.
- Результат `observed` означает только доступность интерфейса.

### Подтверждение

- Запускается локальный SMB receiver.
- Callback принимается только от выбранных адресов.
- Выполняются разрешённые методы coercion.
- Фиксируется входящее NTLM-событие.
- Hash сохраняется для разрешённого офлайн-аудита.

Отсутствие callback означает `incomplete`, а не «цель защищена».

## 14. Логика принятия решений

```text
Нет доступных узлов
└─ проверить scope, ICMP-фильтрацию и TCP discovery

Есть AD, но нет пользователей
├─ anonymous LDAP
├─ SAMR/null session
├─ Kerberos baseline enum
└─ внешний username list

Есть пользователи
└─ AS-REP без пароля

Есть учётка или TGT
├─ authenticated LDAP
├─ Kerberoast
├─ AD CS
├─ SMB/WinRM access
└─ построение путей повышения привилегий

Есть подтверждённая точка входа
└─ остановиться, сохранить evidence и согласовать дальнейшую эксплуатацию
```

## 15. Интерпретация результатов

Отрицательный результат принимается только тогда, когда проверка действительно состоялась:

- `confirmed` — уязвимость или значимый факт подтверждены;
- `observed` — объект или возможность обнаружены, но эксплуатация не доказана;
- `negative` — цель дала однозначный отрицательный ответ;
- `denied` — проверка запрещена политикой доступа;
- `incomplete` — данных недостаточно;
- `error` — техническая ошибка;
- `skipped` — проверка намеренно не запускалась.

Timeout, фильтрация, несовместимый шаблон и отказ доступа не должны превращаться в утверждение «уязвимость отсутствует».

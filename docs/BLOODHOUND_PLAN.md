# BloodHound: варианты сбора для wscan

Исследование: 2026-10-12. Первый LDAP-профиль CE реализован; остальные этапы — план.
Текущие ограничения: [BLOODHOUND.md](BLOODHOUND.md).

## Legacy, CE и OpenGraph

- Legacy: старые BloodHound 4.2/4.3. В BloodHound.py для них используется
  ветка master и команда `bloodhound-python`.
- Community Edition: современный BloodHound. Для Python есть отдельная
  ветка `bloodhound-ce` и команда `bloodhound-ce-python`; официальный
  Windows-коллектор — SharpHound CE. Совместимость нужно проверять для
  выбранной версии сервера и коллектора, а не менять только `meta.version`.
- OpenGraph: расширения CE/Enterprise для собственных типов узлов, связей
  и свойств. Подходит для нашего сетевого инвентаря и наблюдений wscan;
  это отдельная схема, не замена стандартному AD-коллектору.

Источники: [BloodHound.py](https://github.com/dirkjanm/BloodHound.py),
[SharpHound CE](https://bloodhound.specterops.io/collect-data/ce-collection/sharphound),
[OpenGraph](https://bloodhound.specterops.io/opengraph/overview).

Стандартный AD-экспорт — JSON по типам объектов, с `data` и `meta`, обычно
в ZIP. В проверенном SharpHound writer `DataVersion = 6`; пример на странице
документации всё ещё показывает 5. Версию формата нельзя отождествлять с
версией приложения. Тестовые данные BloodHound содержат v5 и v6.

Источники: [JSON formats](https://bloodhound.specterops.io/integrations/bloodhound-api/json-formats),
[SharpHound writer](https://github.com/SpecterOps/SharpHound/blob/master/src/Writers/JsonDataWriter.cs),
[официальные fixtures](https://github.com/SpecterOps/BloodHound/tree/main/cmd/api/src/test/fixtures/fixtures).

## Что уже есть в исходниках

Добавлен собственный удалённый LDAP-коллектор с AD JSON v6/CE ZIP; живой
импорт в CE ещё не проверен. ACL/AD CS и машинные методы пока не реализованы.

`internal/adscan/access.go` содержит LDAP/LDAPS, вход с паролем или NTLM-хешем,
пагинацию и ограничение числа записей. Аудит читает пользователей, компьютеры,
доверия, политики, делегирование и некоторые другие атрибуты. AD CS аудит
читает CA и шаблоны; есть ограниченный анализ security descriptor.

Наш AccessReport — диагностический отчёт. В запросах не хватает полного
набора SID/GUID и объектов групп/OU/GPO для графа. Некоторые бинарные атрибуты
заменяются текстовой пометкой. Такой отчёт нельзя выдать за полноценный
BloodHound ZIP или восстановить из него все связи задним числом.

Текущая политика проекта требует собственного движка; встроенные Go-библиотеки
разрешены. Поэтому основной вариант — native Go-коллектор. Обёртка внешнего
SharpHound/BloodHound.py потребовала бы отдельного изменения этой политики.

## Предлагаемые этапы

### Обязательное ограничение: сбор только с машины wscan

Весь код коллектора выполняется внутри wscan на машине оператора, Linux или
Windows. К целям идут только сетевые запросы к существующим службам.
Нельзя копировать SharpHound/другой EXE, запускать PowerShell, создавать
службы или задачи, использовать удалённое выполнение команд. Членство
машины оператора в домене не должно быть обязательным; нужны явные домен,
DNS/DC и учётные данные. Совместимость такого входа проверяется отдельно.

Это собственный удалённый Go-коллектор, а не запуск SharpHound на цели.
BloodHound.py подтверждает осуществимость удалённого подхода; использовать
его как внешний движок не предлагается.

| Источник | Удалённый способ | Что получаем / ограничения |
| --- | --- | --- |
| DC | LDAP/LDAPS | Объекты, SID/GUID, группы, доверия, делегирование, ACL, OU/GPO, каталожная часть AD CS |
| SYSVOL | Чтение файлов по SMB | Настройки GPO для локальных групп; применение политик и приоритеты нужно рассчитывать, не выдавать конфигурацию за фактический состав группы |
| Компьютеры | SAMR по DCE/RPC через SMB named pipes | Фактический состав локальных групп; требуется разрешённый Remote SAM |
| Компьютеры | SRVSVC/WKSSVC по DCE/RPC | Разные источники сетевых сессий и вошедших пользователей; доступность и смысл результатов различаются |
| Компьютеры | LSARPC | Назначения прав и разрешение SID; отдельные операции требуют дополнительных прав |
| CA/DC | Remote Registry, если служба уже доступна | Дополнительные настройки AD CS/защиты; не включать службу автоматически, отказ означает неполные данные |

Основные соединения: DNS 53, LDAP 389 либо LDAPS 636; SMB 445 для SYSVOL
и выбранных RPC-интерфейсов. Kerberos требует доступного KDC (88), корректных
DNS/FQDN и времени. GC 3268/3269 — дополнительный источник для леса,
не замена LDAP-чтению всех атрибутов. RPC over TCP с 135 и динамическими
портами не нужен базовому LDAP-профилю; отдельный транспорт добавлять только
для конкретного метода, которому недостаточно named pipes.

Профили:

- «Домен»: только DC и, по выбору, чтение SYSVOL. Первым реализуется LDAP;
  обращения ко всем рабочим станциям отсутствуют.
- «Домен + компьютеры»: та же база плюс явный список/область компьютеров
  для удалённых SMB/RPC-запросов, отдельные лимиты параллелизма и таймауты.
- Каталог и сетевой scope — разные ограничения: DC возвращает объекты всего
  выбранного домена/OU, даже если их адреса вне сканируемой подсети. Наличие
  объекта в LDAP не разрешает автоматически опрашивать его хост. Переход по
  довериям, LDAP referrals и запросы в другие домены только в заданной области.

Без доменной учётки существующий ADScan остаётся разведкой. Не показывать
его как полноценный BloodHound-сбор. С доменной учёткой и доступом лишь к DC
можно получить полезную доменную часть графа; отсутствие доступа к компьютерам
не должно останавливать этот экспорт. Отсутствующие сессии, локальные права
и конфигурации отмечаются как «не собраны», без выдуманных связей.

Источники: [удалённый Python-коллектор](https://github.com/dirkjanm/BloodHound.py),
[методы и права](https://bloodhound.specterops.io/collect-data/sharphound-data-permissions).

| Этап | Данные | Доступ / сложность |
| --- | --- | --- |
| 1. LDAP-база → CE ZIP | Users, Computers, Groups, Domains, OU, GPO, Containers; членство, containment, trusts | Доменная учётка с правами чтения; существенная работа по идентификаторам и связям |
| 2. ACL и AD CS | Security descriptors, владельцы, права на объекты, CA/шаблоны и опубликованные связи | Чтение соответствующих LDAP-атрибутов; полноценный парсер прав и GUID |
| 3. Данные машин | Локальные группы, назначения прав, сессии, доступные конфигурации SMB/LDAP | Дополнительные RPC/SMB и права на конкретных машинах; отдельный профиль |
| 4. OpenGraph | Хосты, сервисы, находки и источники наблюдений wscan | Собственная схема расширения и проверка её импорта |
| 5. Legacy | Отдельный сериализатор общих AD-данных | Не преобразование только номера версии; отдельный тест импорта |

LDAP-структуру обычно может читать обычная аутентифицированная доменная
учётка. Domain Admin не обязателен. Сбор локальных групп, прав и сессий имеет
другие требования: на современных Windows часть методов требует локального
администратора или специально делегированного доступа. Нельзя обещать полный
граф по одной анонимной проверке открытых портов.

Источники: [права коллектора](https://bloodhound.specterops.io/collect-data/sharphound-data-permissions),
[методы SharpHound](https://bloodhound.specterops.io/collect-data/ce-collection/sharphound-flags).

## Что должно быть в первой реализации

- Форма: домен, DC, DNS, сохранённая учётка, формат CE, профиль LDAP,
  область домена/OU, отдельный scope компьютеров, лимиты и каталог экспорта.
- Внутренняя модель объектов и связей отдельно от сериализаторов CE/Legacy.
- Идентификаторы SID/GUID, разрешение DN→ID, primary group, foreign security
  principals и чтение больших групп с range retrieval.
- Признаки собранных/не собранных данных и частичных ошибок. Отказ чтения
  сессий не должен превращаться в подтверждение «сессий нет».
- Поддержка требований аутентификации LDAP: signing/channel binding,
  Kerberos/ccache как отдельная работа; текущего пароль/NTLM входа недостаточно
  для обещания работы в любой конфигурации AD.
- Задача в `g`: этап, количество объектов/связей, ошибки, отмена, журнал,
  путь к ZIP. Не передавать пароли в аргументах процесса или в журнале.
- ZIP-экспорт и сводка полноты сбора в wscan. Импорт через UI BloodHound
  сначала; отправка через API — отдельная последующая интеграция.

## Проверка готовности

1. Unit tests SID/GUID, членства, primary group, больших групп и ACL.
2. Тесты ZIP/JSON по выбранным версиям схемы и официальным fixtures.
3. Реальный импорт тестового домена в выбранную версию CE: не только успешная
   загрузка, но правильное число узлов и связи MemberOf/Contains/Trusts.
4. Проверка недоступных атрибутов, лимитов и обрыва LDAP; вывод полноты сбора.
5. Legacy объявлять поддержанным после отдельного импорта в Legacy.
6. Проверить сбор с Linux и Windows вне домена; в тестовой сети запретить
   удалённый запуск и запись на цели. LDAP-профиль должен работать без SMB
   к рабочим станциям; машинный профиль — не выходить за заданный scope.

Предложение: начать с CE и LDAP-базы. Следом ACL/AD CS; машинные методы и
OpenGraph выделить отдельно. Это даст полезный проверяемый результат и
сохранит кроссплатформенность приложения.
